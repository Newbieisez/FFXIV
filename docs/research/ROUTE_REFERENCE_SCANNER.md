# EZBuddy Route Reference Scanner

The Route Reference Scanner inventories RebornBuddy-style profile/source folders so EZBuddy can understand **coverage** without copying third-party navigation routes into the native duty system.

## Clean-room rule

The scanner is a research/indexing tool, not a route importer.

It may report:

- relative source filename/path
- SHA-256 source fingerprint
- inferred duty category (Dungeon, Trial, Raid, Alliance Raid, Duty)
- count of waypoint-like constructs
- explicit queue/duty IDs when present
- explicit territory/zone/map IDs when present
- NPC/boss IDs when explicitly named
- object/data/interact IDs when explicitly named
- action/spell/cast IDs when explicitly named
- fixed interaction labels such as Door, Switch, Lift, Chest, Boss, Interact, Loot

It intentionally does **not** report or persist:

- X/Y/Z coordinates
- Vector3 values
- positions or destinations
- raw profile bodies
- copied encounter scripts
- copied profile comments/descriptions

Third-party profile material stays reference-only unless its license explicitly permits reuse and we intentionally choose to comply with that license. EZBuddy's native `DutyNavigationProfile` routes remain generated by our own in-game recorder/verification process.

## Scan local RebornBuddy folders

The scanner accepts multiple roots in one pass:

```powershell
EZBuddy.RouteReferenceScanner.exe scan `
  --source "My RebornBuddy folders" `
  --out "EZBuddy-route-reference-manifest.json" `
  --root "C:\RebornBuddy\Profiles" `
  --root "C:\RebornBuddy\Plugins" `
  --root "C:\RebornBuddy\BotBases"
```

Supported source formats are `.xml`, `.json`, and `.cs`.

The output never stores the absolute scan-root path, which avoids leaking a Windows username or local folder layout when manifests are shared.

## How the manifest feeds duty development

1. Scan all available profile packs.
2. Deduplicate entries by source fingerprint and duty/category clues.
3. Build a coverage list of dungeons, trials, raids, and alliance raids.
4. Extract only IDs and objective-type clues needed to plan clean-room capture.
5. Record the duty in game with `DutyRouteRecorder`.
6. Compare the recorded route against the coverage manifest for missing doors, switches, lifts, chests, boss boundaries, or mechanic observations.
7. Verify the native JSON route in game before marking the duty supported.

## Security controls

- XML DTD processing is prohibited and external XML resolution is disabled.
- Files above the configured size limit are skipped/rejected.
- Directory scans have a maximum file count.
- Malformed individual sources do not abort an otherwise valid directory scan.
- The manifest schema has no coordinate-bearing fields.

This separation lets EZBuddy learn *what needs coverage* from existing ecosystems while keeping the actual executable navigation data original and verifiable.
